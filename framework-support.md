# Supported Frameworks & Languages Specification

**Project:** Automation Script Quality Auditor  
**STLC Phase:** Phase 1 — Requirement Analysis & Planning  
**Task Reference:** T02 — Define Supported Frameworks  
**Status:** Approved Specification  

---

## 1. Overview & Purpose

The **Automation Script Quality Auditor** is a lightweight static analysis tool designed to help QA engineers and test automation practitioners identify anti-patterns, maintainability issues, and code smells in their test automation scripts.

The purpose of this document is to formally define:
* The test automation frameworks and programming language bindings supported in the initial version.
* The primary analysis areas evaluated for each framework.
* The operational boundaries and limitations of static analysis.
* The distinction between framework-agnostic (common) checks and framework-aware checks.

---

## 2. Supported Frameworks & Language Matrix

The initial version of the auditor supports **three** major automation frameworks across **three** primary programming languages:

| Framework | Supported Languages | Typical File Extensions | Execution Mode in Auditor |
| :--- | :--- | :--- | :--- |
| **Selenium** | Python | `.py` | Static Analysis Only (No Execution) |
| **Playwright** | Python, JavaScript, TypeScript | `.py`, `.js`, `.ts` | Static Analysis Only (No Execution) |
| **Cypress** | JavaScript, TypeScript | `.js`, `.ts` | Static Analysis Only (No Execution) |

### 2.1 Selenium
* **Supported Language:** Python
* **Scope:** Static inspection of Python automation scripts using the Selenium WebDriver bindings (`selenium.webdriver`).
* **Relevant Analysis Areas:**
  * **Wait Patterns:** Identification of unconditional pauses (e.g., `time.sleep()`), misuse of implicit waits, and missing explicit waits (`WebDriverWait`).
  * **Locators:** Detection of brittle locator strategies (e.g., absolute XPaths, raw DOM indexes, dynamic autogenerated IDs).
  * **Assertions:** Verification that test steps culminate in verifiable assertions (`assert` statements or test framework assertion methods).
  * **Test Structure:** Structure of setup/teardown hooks, modularity, and adherence to clean test isolation.
  * **Automation Anti-patterns:** Common automation anti-patterns including hardcoded test data, duplicated driver commands, and missing teardown handlers.

### 2.2 Playwright
* **Supported Languages:** Python, JavaScript, TypeScript
* **Scope:** Static inspection of Playwright automation scripts adhering to Python (sync/async) and Node.js (JS/TS) conventions (`@playwright/test` or `playwright`).
* **Relevant Analysis Areas:**
  * **Wait Patterns:** Detection of explicit sleep calls (e.g., `page.wait_for_timeout()`, `time.sleep()`) that bypass Playwright's built-in auto-waiting mechanisms.
  * **Locators:** Evaluation of locator practices (e.g., overuse of fragile CSS/XPath versus recommended user-facing locators like `getByRole`, `getByText`, or `getByTestId`).
  * **Assertions:** Inspection of web-first assertions (`expect(locator)...`) versus non-retrying standard assertions.
  * **Test Structure:** Proper handling of `async`/`await` patterns, fixture usage, and test scoping.
  * **Automation Anti-patterns:** Direct DOM manipulation bypasses, unhandled promise chains, and hardcoded test environments.

### 2.3 Cypress
* **Supported Languages:** JavaScript, TypeScript
* **Scope:** Static inspection of Cypress spec files (`.cy.js`, `.cy.ts`) using standard Cypress commands (`cy.*`).
* **Relevant Analysis Areas:**
  * **Wait Patterns:** Flagging fixed millisecond delays (e.g., `cy.wait(5000)`) instead of route aliasing (`cy.wait('@alias')`) or assertion-driven waiting.
  * **Selectors:** Identification of brittle selectors (e.g., complex class hierarchies, CSS chains) instead of dedicated test attributes (e.g., `data-cy`, `data-testid`).
  * **Assertions:** Validation that command chains terminate with appropriate assertion clauses (`.should()`, `.and()`, or `expect()`).
  * **Test Structure:** Proper chaining, avoiding assignment of Cypress return values to synchronous variables, and adhering to Cypress lifecycle hooks (`beforeEach`).
  * **Automation Anti-patterns:** Anti-patterns such as conditional testing in specs, mixing async/await with Cypress commands, and repetitive login UI steps.

## 3. Main Analysis Areas

Across all supported frameworks, the auditor evaluates test scripts across five core quality dimensions:

```
+-----------------------------------------------------------------------+
|                       Script Quality Dimensions                       |
+-----------------------------------------------------------------------+
| 1. Wait Patterns & Synchronization                                    |
|    - Explicit hardcoded delays vs. dynamic/auto-waiting mechanisms    |
+-----------------------------------------------------------------------+
| 2. Locators & Selector Strategies                                     |
|    - Resilient user-facing selectors vs. fragile, brittle DOM paths  |
+-----------------------------------------------------------------------+
| 3. Assertions & Validation                                            |
|    - Meaningful, retry-safe validation vs. missing or empty checks    |
+-----------------------------------------------------------------------+
| 4. Test Structure & Organization                                      |
|    - Modularity, proper lifecycle hooks, and single-purpose tests     |
+-----------------------------------------------------------------------+
| 5. Common Code Smells & Cleanliness                                   |
|    - Hardcoded secrets, magic numbers, duplication, God scripts       |
+-----------------------------------------------------------------------+
```

## 4. Static Analysis Limitation

The Automation Script Quality Auditor is strictly a **static analysis tool**. It inspects and parses the raw source code text provided by the user without compiling or executing the code.

### 4.1 Explicit Operational Boundaries
The initial version will **NOT**:
* **Execute automation scripts:** No script code is evaluated, interpreted, or run in any runtime environment (Python, Node.js).
* **Launch or control browsers:** The tool will not open, manipulate, or automate browser instances (Chrome, Firefox, Safari, Edge).
* **Connect to target websites or networks:** No network requests, API calls, or external web traffic are initiated to target applications under test.
* **Invoke test runners:** The tool will not run `pytest`, `unittest`, `@playwright/test`, `cypress run`, or any test harness.

### 4.2 Architectural Benefits of Static Analysis
* **Safety & Sandboxing:** Users can safely submit scripts containing syntax errors or untrusted code without risk of unwanted side effects or remote code execution.
* **Speed & Responsiveness:** Static checks execute instantaneously without waiting for network latency, browser startup, or test timeouts.
* **Portability:** Zero runtime dependencies on browser binaries (Chromium, Firefox, WebKit), display servers, or test framework drivers.

## 5. Common vs. Framework-Aware Analysis

The auditor partitions its rule catalog into two distinct layers: **Common (Framework-Agnostic) Checks** and **Framework-Aware Checks**.

```
+---------------------------------------------------------------+
|                       Auditor Rules Engine                    |
+-------------------------------+-------------------------------+
|    Common Analysis Rules      |   Framework-Aware Rules       |
|   (Evaluated for all scripts) |  (Activated by user selection)|
+-------------------------------+-------------------------------+
| • Magic numbers / constants   | • Selenium-specific rules     |
| • Duplicated code blocks      | • Playwright-specific rules   |
| • Poor test structure         | • Cypress-specific rules      |
| • Missing abstractions        | • Framework locator syntax    |
| • Hardcoded secrets & tokens  | • Framework wait commands     |
| • Testing implementation data | • Framework assertion types   |
+-------------------------------+-------------------------------+
```

### 5.1 Common Analysis Areas (Framework-Agnostic)
These quality checks reflect universal software engineering and test automation hygiene principles. They apply regardless of the selected framework:

1. **Magic Numbers / Hardcoded Values:**
   * Unnamed numerical constants or arbitrary thresholds directly embedded within test logic.
2. **Duplicated Code:**
   * Repeated sequences of actions or copy-pasted blocks that should be centralized.
3. **Poor Test Structure:**
   * Oversized "God" tests executing dozens of unrelated scenarios within a single test block.
4. **Missing Abstractions:**
   * Direct inlining of UI element manipulation without abstraction layers (e.g., absence of Page Object Model or helper utilities).
5. **Hardcoded Secrets & Credentials:**
   * Plaintext passwords, API keys, bearer tokens, or sensitive environment URLs embedded directly in the script.
6. **Testing Implementation Details:**
   * Targeting internal component state or layout styling instead of user-observable functionality.

### 5.2 Framework-Aware Analysis Areas (Framework-Specific)
These rules inspect syntax constructs, function calls, and design patterns unique to each specific automation library and language binding:

1. **Hardcoded Waits:**
   * *Selenium (Python):* Flags `time.sleep(<seconds>)` calls.
   * *Playwright (Python/JS/TS):* Flags `page.wait_for_timeout(<ms>)` calls.
   * *Cypress (JS/TS):* Flags `cy.wait(<number>)` calls with numeric durations.
2. **Fragile Locators & Selectors:**
   * *Selenium (Python):* Flags long hierarchical XPaths (e.g., `/html/body/div[2]/div[1]/...`) or unstable `By.CLASS_NAME` hooks.
   * *Playwright (Python/JS/TS):* Recommends migrating from brittle CSS/XPath chains to role-based locators (`page.get_by_role()`, `page.locator("[data-testid=...]")`).
   * *Cypress (JS/TS):* Flags brittle selector chaining (e.g., `cy.get('div > div > span:nth-child(2)')`) in favor of dedicated test attributes (`cy.get('[data-cy=...]')`).
3. **Missing or Inadequate Assertions:**
   * *Selenium (Python):* Detects sequences of actions containing zero `assert` or validation statements.
   * *Playwright (Python/JS/TS):* Detects absence of `expect(locator)` checks or reliance on synchronous assertions that do not retry.
   * *Cypress (JS/TS):* Detects command chains lacking terminal `.should()` assertions.
4. **Potentially Flaky Patterns:**
   * Framework-specific hazards such as mixing sync/async in Playwright, misuse of Cypress asynchronous aliases, or improper element state checks prior to interaction.

## 6. Context Activation Mechanism

When the user submits a script:
1. The **selected framework** (Selenium, Playwright, or Cypress) and target language establish the active rule set.
2. The auditor runs the universal **Common Rules** across all scripts.
3. The auditor applies the specialized **Framework-Aware Rules** corresponding to the selected framework.
4. Detection results are aggregated, scored, and prepared for reporting and AI remediation suggestions.
